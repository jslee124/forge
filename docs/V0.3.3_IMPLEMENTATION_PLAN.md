# Forge v0.3.3 Implementation Plan

[简体中文](zh-CN/V0.3.3_IMPLEMENTATION_PLAN.md) · [Roadmap](ROADMAP.md) · [Context management](CONTEXT_MANAGEMENT.md)

## Status and purpose

This is the detailed design and implementation record for Roadmap Milestone 13.
Sections 13.0-13.5 are implemented on the development branch. Automatic
compaction remains opt-in because the live semantic-quality gate was not run;
this document is not evidence that v0.3.3 has been published.

The release theme is **long-session efficiency and user control**. Four product
problems are addressed together because they share the same runtime, TUI,
trace, and trust boundaries:

1. Context pressure must be visible and automatically manageable.
2. Safe workflows must not require repetitive identical approvals.
3. Available updates must appear inside the TUI without interrupting work.
4. Prompt-cache behavior must be measurable before Forge claims to optimize it.

## Decisions captured from design discussion

The following decisions are part of the plan unless implementation evidence
causes the Roadmap to change:

- The current deterministic extractive checkpoint remains a fallback and test
  oracle. It is not sufficient evidence for making automatic compaction the
  default.
- The default remains `warn` until deterministic and opt-in live quality gates
  pass. Users must still be able to discover and enable auto compaction without
  editing JSON.
- Context pressure is always visible near the editor as a segmented ring plus a
  percentage. `/context` expands the same snapshot into an interactive panel.
- A percentage means projected next-request input divided by available input,
  not transcript history divided by the raw model window.
- Auto compaction can be enabled for the current session without persistence.
  Saving it as the user default requires a separate explicit action.
- Permission improvements use narrow, inspectable session grants. v0.3.3 does
  not add persistent unrestricted grants or restore grants on resume.
- Update discovery is asynchronous and non-blocking. Installation remains an
  explicit action and must respect the detected installation source.
- Cache telemetry and stable-prefix hashing land before default compaction
  changes, so cost and latency effects can be compared with a baseline.

## Current baseline

Forge already has useful foundations, but not the complete experience:

| Area | Implemented baseline | v0.3.3 gap |
| --- | --- | --- |
| Context | Per-step budgets, pressure snapshot/ring, interactive `/context`, session/default auto controls, canonical transcripts, checkpoints, `/compact`, no-progress pause, and bounded overflow recovery | The extractive fallback has not passed the live production-quality gate, so `warn` remains default |
| Permissions | Structured allow-once/session/deny responses, normalized scopes, high-risk re-confirmation, `/permissions`, denial feedback, and plugin policy tightening | Grants intentionally remain memory-only and are never restored |
| Updates | Structured cached/refreshing/available/current/failed/disabled state, live Ink banner, dismissal, bounded registry fetch, explicit npm/pnpm install, and unknown-provenance refusal | Installation remains explicit and the running process requires restart |
| Cache | Provider-qualified read/write usage, per-step and aggregate ratios, stable-prefix hashes, invalidation reasons, and cache capability descriptors | Keyed/breakpoint controls remain disabled until a concrete adapter endpoint declares and tests them |

Primary implementation anchors:

- `packages/core/src/context.ts` and `packages/core/src/runtime.ts`
- `packages/core/src/policy.ts` and `packages/core/src/model.ts`
- `packages/persistence/src/session-store.ts` and `trace-store.ts`
- `apps/cli/src/persistent-session.ts`, `run.ts`, `interactive-ui.tsx`,

## Product and security invariants

These constraints take precedence over convenience:

- The canonical transcript remains lossless; compaction changes only the active
  model view and checkpoint metadata.
- Current instructions, the current request, required tool schemas, pending
  protocol state, and required tool results cannot be silently discarded.
- A checkpoint is untrusted historical memory. It cannot grant approval,
  restore trust, change policy, or establish current verification status.
- Project files may tighten context behavior but cannot persist a user grant,
  widen permissions, choose an update installer, or disable user-required
  guards.
- Provider-specific cache and compaction mechanisms remain inside adapters.
  Core consumes capabilities and normalized events.
- Unknown telemetry stays unknown. Forge must not turn missing cache usage into
  zero, or a conservative token estimate into an exact percentage.
- Update state never enters the model prompt, transcript, or session memory.
- No v0.3.3 path modifies existing credentials, configuration, sessions,
  traces, or plugins as a side effect of checking for or displaying an update.

## Architecture overview

```text
editor draft + attachments
          |
          v
ContextProjectionService -----> ContextPressureSnapshot
          |                              |
          |                              +--> persistent footer ring
          |                              +--> interactive /context panel
          |                              +--> activation prompt
          v
preflight budget --> compaction coordinator --> active request view
                           |                         |
                           +--> checkpoint store    +--> model adapter

tool proposal --> core policy --> scope matcher --> approval channel --> execute
                                      |                    |
                                      +--> session grants  +--> TUI panel

model finish --> cache observation --> trace/inspect --> next-prefix diagnostics

update cache/fetch --> UpdateState store --> TUI banner --> explicit installer
```

The four features share structured events and presentation, but their authority
does not mix. A context choice cannot approve a tool; an update notification
cannot consume editor input; a cache key cannot become a permission identity.

## 1. Context pressure, auto compaction, and TUI controls

### 1.1 Pressure definition

The primary UI ratio is:

```text
pressure = projectedInputTokens / availableInputTokens
availableInputTokens = contextWindowTokens - max(outputReserve, safetyBuffer)
```

`projectedInputTokens` includes the content Forge expects to send next:

- effective system/project instructions;
- stable Skill/resource catalog metadata and selected resource content;
- advertised tool schemas;
- active checkpoint memory and retained verbatim turns;
- provider continuation and required tool results where applicable;
- current editor draft and attached image estimates.

The idle estimate may use the conservative local estimator and must not make a
provider request. Exact provider usage from the previous step is calibration
evidence, not a replacement for projecting the next request.

Suggested shape:

```ts
interface ContextPressureSnapshot {
  readonly schemaVersion: 1;
  readonly modelId: string;
  readonly estimatedInputTokens: number;
  readonly availableInputTokens: number;
  readonly ratio: number;
  readonly confidence: "exact" | "estimated" | "unavailable";
  readonly mode: "warn" | "auto-session" | "auto-default" | "paused";
  readonly state:
    | "normal"
    | "elevated"
    | "compact-soon"
    | "compacting"
    | "compacted"
    | "critical"
    | "paused";
  readonly lastCompaction?: ContextCompactionSummary;
}
```

This is an illustrative contract. The implemented schema must be versioned and
validated where it crosses persistence or trace boundaries.

### 1.2 Persistent context ring

The first footer row owns model, effort, and context status. The second row
keeps the existing shortcuts readable:

```text
› Describe what you want Forge to do...

  gpt-5.x · high                              ◑ 58% context · warn
  Shift+Tab effort · Enter submit · Ctrl+C cancel
```

Ring levels provide quick shape recognition while the number carries meaning:

| Projected pressure | Glyph | Semantic state |
| --- | --- | --- |
| 0-24% | `○` | normal |
| 25-49% | `◔` | normal |
| 50-74% | `◑` | elevated |
| 75-89% | `◕` | warning / compact soon |
| 90%+ | `●` | critical |

Color is supplementary and cannot be the only signal. When confidence is
estimated, render `~78%`; when unavailable, render `?`. Responsive behavior:

```text
wide     ◕ 78% context · auto
narrow   ◕ 78%
minimal  ◕
```

Draft changes should update the local projection with debounce or cheap memoized
calculation. The ring must not cause cursor jitter, steal keyboard ownership,
or trigger a provider call.

### 1.3 Interactive `/context` panel

`/context` and the ring read the same snapshot. The panel adds controls:

```text
╭ Context management ─────────────────────────╮
│ Model          gpt-5.x                      │
│ Pressure       ◕ 78% · estimated            │
│ Mode           Warn only                    │
│ Strategy       Provider native -> summary   │
│ Recent tail    12K tokens                   │
│ Last compact   Never                        │
│                                             │
│ a  Enable auto compact                      │
│ c  Compact now                              │
│ p  Preview compaction                       │
│ Esc close                                   │
╰─────────────────────────────────────────────╯
```

Enabling auto opens a second choice:

```text
1  Enable for this session
2  Save as my user default
3  Cancel
```

Session mode remains memory-only. User-default mode updates user configuration
through the existing validated and atomic config path. Project configuration
cannot initiate either action.

### 1.4 Activation and compaction state machine

```text
warn
  | threshold crossed once
  v
offer: compact once / auto-session / dismiss
  | auto enabled
  v
monitor pressure --> compact-soon --> compacting
                                      | success
                                      v
                                  compacted --> monitor
                                      |
                            failure or low reclaim
                                      v
                                    paused
```

Initial experiments use 75-80% projected pressure as the activation range. The
final threshold belongs to model capabilities/configuration and evaluation
evidence, not presentation code. The coordinator should also consider projected
growth and minimum useful reclamation so it does not compact every turn.

The first no-progress hypothesis is to pause when reclamation is less than the
larger of 8,000 tokens or 20% of projected input. This is a tuning value, not a
public compatibility guarantee.

### 1.5 Compaction pipeline

The coordinator runs only at safe boundaries:

1. Recompute the final request budget.
2. Preserve mandatory instructions/current request/protocol state.
3. Bound or replace stale completed tool outputs.
4. Select only a completed historical prefix; retain a configured recent tail.
5. Prefer adapter-native opaque compaction when declared and round-trippable.
6. Otherwise generate a structured Forge summary and validate its size, safety
   labels, provenance, source hash, and retained-tail hash.
7. Keep the deterministic extractive checkpoint only as fallback.
8. Re-budget the resulting request and require meaningful reclamation.
9. Persist the checkpoint atomically while preserving the canonical transcript.
10. Emit completed/failed/paused events and update the UI snapshot.

The structured summary should retain only future-relevant historical facts:

```ts
interface ForgeConversationSummary {
  readonly userGoals: readonly string[];
  readonly constraints: readonly string[];
  readonly decisions: readonly { decision: string; reason?: string }[];
  readonly touchedFiles: readonly string[];
  readonly completedWork: readonly string[];
  readonly unresolvedWork: readonly string[];
  readonly historicalVerification: readonly string[];
}
```

Every field is untrusted memory. `historicalVerification` must explicitly mark
that results came from an earlier run and are not current proof. Approval and
credential fields are forbidden rather than merely discouraged.

### 1.6 Compaction feedback

The transcript receives concise system status, not the summary body:

```text
✓ Context compacted · 86K -> 34K
  Provider-native · retained 6 recent turns
```

or:

```text
⚠ Compaction reclaimed only 4%
  Automatic compaction paused to avoid a loop
```

The UI may report separately measured generation usage, but must not estimate a
monetary price without current provider pricing and explicit product support.

## 2. Scoped permission system

### 2.1 Core decision model

The approval channel must return a structured response instead of `boolean`:

```ts
type ApprovalResponse =
  | { readonly decision: "allow-once" }
  | {
      readonly decision: "allow-session";
      readonly scope: ApprovalScope;
    }
  | { readonly decision: "deny"; readonly feedback?: string };
```

The policy still decides `allow`, `confirm`, or `deny`. Only a `confirm` result
may reach the approval channel, and core decides which candidate scopes the UI
may offer. The model cannot author its own grant scope.

Each proposed action supplies an approval descriptor:

```ts
interface ApprovalDescriptor {
  readonly actionId: string;
  readonly title: string;
  readonly effect: "read" | "write" | "process" | "network" | "model";
  readonly target: Readonly<Record<string, string | number | boolean>>;
  readonly riskFlags: readonly string[];
  readonly preview: ApprovalPreview;
  readonly allowedSessionScopes: readonly ApprovalScope[];
}
```

### 2.2 Scope identities

| Action | Candidate session identity | Must re-prompt when |
| --- | --- | --- |
| Workspace write | canonical workspace plus displayed file/directory scope | canonical path escapes scope, workspace changes, or action becomes destructive |
| Process | program, exact arguments or explicitly supported prefix, cwd, environment class, timeout ceiling | argument/cwd changes, timeout grows, shell semantics appear, or risk flag changes |
| Network | tool identity, scheme, canonical host, optional port | redirect/destination/tool changes or private-network policy changes |
| Delegated model | registered tool/subagent identity and bounded role | task crosses displayed role, tool set changes, or budget grows beyond the grant |

Do not fingerprint unresolved globs, shell-rendered display strings, or natural
language explanations. Matching uses the same canonical values execution uses.

### 2.3 Session grant lifecycle

- Grants belong to one active session and canonical workspace.
- They are kept in memory by default and are not written into session snapshots.
- `/resume`, `/new`, process restart, workspace change, and explicit revoke clear
  them.
- Trace events record the scope ID, decision, provenance, and use count for
  audit, but trace replay never recreates authority.
- Destructive, credential-sensitive, publish/install, broad external-effect,
  and policy-designated operations always re-confirm or deny.
- Plugin policy hooks can make a decision stricter but cannot add candidate
  scopes or convert deny/confirm into allow.

### 2.4 Approval and `/permissions` UI

```text
╭ Approval required ──────────────────────────╮
│ $ pnpm test                                 │
│ Working directory  /workspace               │
│ Scope offered      exact command this session│
│                                             │
│ 1  Allow once                              │
│ 2  Allow this scope for the session         │
│ 3  Deny                                    │
╰─────────────────────────────────────────────╯
```

`/permissions` shows the effective profile and provenance, active grant scopes,
use counts, high-risk overrides, and revoke controls. Deny may optionally accept
bounded feedback such as "run the targeted test only"; feedback returns as a
denial result and never implies approval.

## 3. Prompt-cache optimization

### 3.1 Measurement first

For every provider step, normalize when available:

```ts
interface PromptCacheObservation {
  readonly inputTokens?: number;
  readonly cacheReadTokens?: number;
  readonly cacheWriteTokens?: number;
  readonly uncachedInputTokens?: number;
  readonly hitRatio?: number;
  readonly stablePrefixHash: string;
  readonly capability: "automatic" | "keyed" | "breakpoints" | "unsupported";
  readonly invalidationReasons: readonly string[];
}
```

`hitRatio` is calculated only when the provider's usage semantics establish the
needed values. `undefined` remains unavailable through trace schema, summary,
and UI.

### 3.2 Stable prefix layout

```text
stable prefix
  1. Forge core contract and prompt-schema version
  2. resolved user/project instructions in deterministic order
  3. stable Skill/resource catalog metadata
  4. stable tool definitions and JSON schemas

dynamic suffix
  5. explicitly selected or loaded Skill content
  6. per-turn plugin prompt contributions
  7. context checkpoint memory
  8. retained conversation and continuation
  9. current request, images, and tool results
```

The exact provider serialization may constrain this layout. Adapters must expose
what can actually be held stable rather than core assuming identical wire
formats.

### 3.3 Cache key and invalidation

A supported keyed cache may derive a non-secret identifier from:

```text
provider + model + promptSchemaVersion + canonicalWorkspaceId
+ instructionHash + resourceCatalogHash + toolSchemaHash
```

The current user prompt is not part of the stable key. The key contains hashes,
not raw paths or prompt text sent as metadata unnecessarily.

| Change | Expected result |
| --- | --- |
| User request only | stable prefix remains |
| Provider/model | invalidate |
| Instruction content/order | invalidate |
| Enabled Skill/plugin or tool schema | invalidate |
| Reasoning/provider option that changes request semantics | invalidate |
| New compaction checkpoint | intentional new prefix |
| Tool result appended to an unchanged continuation | preserve earlier prefix where the protocol allows |

`forge inspect` reports actual provider cache usage and local likely-invalidating
changes separately. A local matching hash is not proof of a provider hit.

## 4. In-TUI update experience

### 4.1 Structured update service

The current checker becomes a state producer:

```ts
type UpdateState =
  | { readonly kind: "disabled" }
  | { readonly kind: "cached"; readonly latest: string; readonly checkedAt: string }
  | { readonly kind: "refreshing"; readonly previous?: string }
  | { readonly kind: "current"; readonly checkedAt: string }
  | { readonly kind: "available"; readonly latest: string; readonly checkedAt: string }
  | { readonly kind: "failed"; readonly retryAfter?: string };
```

The service preserves the 24-hour cache, bounded timeout, atomic owner-only
cache file, CI suppression, and environment opt-out. Expected background
failures remain quiet; explicit `forge update check` remains verbose and
authoritative.

### 4.2 TUI behavior

An available state renders inside Ink and outside model history:

```text
╭ Update available ───────────────────────────╮
│ Forge 0.3.3 -> 0.3.4                        │
│ Run `forge update` · Release notes · Dismiss│
╰─────────────────────────────────────────────╯
```

- A cached result may render immediately.
- A fresh result may update the active TUI asynchronously.
- The banner cannot steal input from editor, approval, login, or another modal.
- Dismissal is per version; the explicit command remains available.
- Narrow terminals wrap or abbreviate without hiding the version transition.
- Update status is UI/application state, not a transcript message.

### 4.3 Installation provenance

Before installing or printing an exact command, resolve a supported provenance
such as npm-global or pnpm-global from executable/package metadata and bounded
environment evidence. Do not infer Homebrew or another manager from a path
substring alone. Unknown provenance receives version and documentation guidance
but no guessed global install.

Installation remains explicit, uses `program + args[]` with `shell: false`,
keeps lifecycle scripts disabled where the supported installer allows it, and
states that restart is required. `$FORGE_HOME` data is outside the replacement
artifact and is checked before and after install tests.

## 5. Events, persistence, and compatibility

Planned event families:

- `context.pressure.updated`, `context.auto.enabled`,
  `context.auto.paused`, and existing compaction events with richer result data;
- `approval.scope.offered`, `approval.scope.granted`,
  `approval.scope.matched`, and `approval.scope.revoked`;
- `model.cache.observed` and `model.cache.invalidated`;
- application-level update state for the TUI, with trace events only for an
  explicit update command rather than passive startup noise.

Persistence rules:

- Context checkpoints remain versioned, hash-validated session data.
- Session auto mode and permission grants are ephemeral unless a user explicitly
  saves only the context default to user configuration.
- Dismissed update versions belong to user-level application state, not project
  configuration.
- New optional trace fields must remain readable by old summaries; missing
  fields are unavailable, not zero.

## 7. Test and evaluation plan

### Deterministic unit and integration tests

- Exact pressure arithmetic, reserve counted once, draft/image projection,
  unknown model fallback, and percentage confidence.
- Threshold crossing, one-time activation offer, session/default selection,
  compact success/failure/cancellation, and no-progress pause.
- Summary schema validation, redaction, source/tail hashes, resume equivalence,
  and canonical transcript preservation.
- Stable prefix and every invalidation input; missing cache usage; aggregation;
  append-only continuation; post-compaction prefix change.
- Approval once/session/deny, exact and near-match scope tests, revoke, workspace
  changes, timeout ceiling, destructive override, plugin tightening, and resume.
- Cached/fresh update state, late delivery, malformed semver, timeout,
  CI/disabled behavior, dismissal, provenance, failed install, and data
  protection.

### Visual and interaction tests

Render at representative narrow and wide widths:

- editor with each ring/state/confidence value;
- two-row footer without changing Enter, Shift/Meta+Enter, Ctrl+J, or Ctrl+C;
- `/context`, activation, approval, and `/permissions` panels;
- update banner arriving while editing, streaming, and awaiting approval;
- long paths, commands, versions, translated labels, and `NO_COLOR`.

String assertions alone are not visual acceptance. Capture real rendered frames
and inspect alignment, wrapping, contrast, cursor ownership, and scrollback.

### Long-session evaluation fixtures

Each fixture records task completion plus whether Forge retained:

- the user's current goal and explicit constraints;
- edited and relevant files;
- completed work versus unresolved work;
- decisions and their reasons;
- historical verification provenance without claiming it is current;
- safety behavior when old text requests approval or policy changes.

Compare `warn`, `auto-session`, and user-default auto modes on identical inputs.
Measure estimated/provider tokens, cache read/write, compaction count, reclaimed
tokens, latency, approval count, time awaiting approval, and no-progress pauses.

Live provider trials are explicit opt-in and never part of the default test
suite. Provider-specific cache or compact claims require current first-party
documentation plus observed, redacted usage evidence.

## 9. Release gates

v0.3.3 is ready only when:

- deterministic long-session fixtures preserve goals, constraints, touched
  files, unresolved work, resume, and safety behavior;
- live quality thresholds recorded before rollout justify any default change;
- the context indicator is truthful, responsive, and connected to actionable
  controls;
- representative scoped grants reduce duplicate approvals while every
  near-match and high-risk fixture re-prompts or denies;
- cache calculations are correct and provider-qualified, with no universal
  hit-rate promise;
- update discovery is non-blocking, install-aware, explicit, and leaves existing
  `$FORGE_HOME` data unchanged;
- build, check, full offline tests, docs/link checks, deterministic evaluations,
  packed-artifact verification, installed CLI smoke tests, and version
  consistency pass for `0.3.3`.

If the compaction quality gate does not pass, v0.3.3 may still ship the ring,
interactive controls, session opt-in, scoped permissions, cache telemetry, and
update banner while keeping `warn` as the honest default.

## 10. Open decisions to resolve with evidence

- Final pressure thresholds per model capability and whether projected growth
  needs a separate trigger.
- Which Forge/provider model generates a fallback structured summary, its cost
  ceiling, and cancellation behavior.
- Whether exact-command session grants are sufficient or a small audited set of
  structured command families is needed.
- Which installation provenances can be detected reliably on macOS, Linux, and
  Windows for v0.3.3.
- Whether prompt-cache controls exposed by current provider SDKs are stable
  enough to enable or should remain telemetry-only for a provider.

These decisions must be recorded in this document and the Roadmap when tests or
current provider behavior settle them.
