# v0.1 Acceptance and Evaluation

## Status

This document is the concrete release contract for Forge v0.1. Product and
architecture documents describe direction; this document defines the evidence
required to claim that the first version works.

## Scope

Forge v0.1 proves one narrow capability:

> Given a small TypeScript repository task, inspect the relevant code, make a
> targeted workspace change, run an approved verification command, react to the
> observed result, and stop with a truthful status and trace.

The release uses DeepSeek as its first real provider. The default test suite
uses a scripted fake model and never requires an API key or paid request.

## Two evidence tracks

Forge separates runtime correctness from model variability.

### Deterministic runtime evidence

A scripted fake `ModelAdapter` produces known model events and tool calls. These
tests prove state transitions, policy decisions, tool execution, failure
recovery, cancellation, limits, and trace consistency. They run in the default
test suite.

### Live provider evidence

Opt-in trials use `deepseek-v4-flash` through `@ai-sdk/deepseek`. They measure
whether the assembled system can solve repository tasks, not whether the
runtime state machine is deterministic. A live failure is recorded as data and
must not be rewritten as success.

## Canonical fixture: `validation-bug`

The first fixture will live at `fixtures/validation-bug` and remain small enough
to understand during an interview.

Planned files:

```text
fixtures/validation-bug/
|-- package.json
|-- src/
|   |-- parse-port.ts
|   `-- server-config.ts
`-- test/
    `-- parse-port.test.ts
```

Initial defect: `parsePort` uses permissive parsing and accepts malformed values
such as `"3000abc"`.

Canonical task prompt:

```text
Make parsePort accept only base-10 integer strings from 1 through 65535.
Reject empty input, whitespace-only input, signs, decimals, exponent notation,
trailing characters, zero, and values above 65535. Preserve the public API,
update tests when useful, and run the repository test command before finishing.
```

Expected behavior:

- Valid examples include `"1"`, `"3000"`, and `"65535"`.
- Invalid examples include `""`, `"  "`, `"+80"`, `"-1"`, `"1.5"`, `"1e3"`,
  `"3000abc"`, `"0"`, and `"65536"`.
- The agent reads at least the implementation, its caller, and the relevant
  tests before finishing.
- Writes remain inside the copied fixture workspace.
- The approved verification command is `pnpm test` from the fixture root.
- Fixture-owned tests and hidden release tests both pass.
- The final summary matches the actual diff and verification result.

Each trial starts from a fresh temporary copy. The grader runs outside the agent
after the run, so the model cannot edit the grader or hidden tests.

## Deterministic recovery scenario

Failure recovery is proved separately rather than forcing every capable live
model to make an initial mistake. A scripted adapter must produce this sequence:

1. Read the implementation and tests.
2. Apply an intentionally incomplete patch.
3. Run the approved verification command and observe a non-zero exit.
4. Use the command output to apply a corrective patch.
5. Run verification again and observe success.
6. Finish with a summary consistent with both attempts.

The test fails if Forge stops after step 3, hides the failed result, skips a
policy decision, or reports success before the passing verification.

## Initial runtime limits

| Limit | Default |
| --- | --- |
| Model steps | `12` |
| Tool calls | `40` |
| Process timeout | `60000` ms |
| Output retained per tool result | `65536` bytes |
| Built-in file access | Selected workspace only |

Reaching a limit produces a `limit_reached` terminal status and exit code `3`.
It is not a successful completion.

## Evaluation approvals

Interactive runs use the normal approval UI. A non-interactive fixture trial
may inject a test approval channel that matches only:

```text
program: pnpm
arguments: ["test"]
working directory: canonical fixture root
timeout: 60000 ms
```

All other process commands require a separate declared approval and are denied
when no approval channel exists. The fixture approval cannot authorize file
access outside the fixture workspace or enable a broader permission profile.

## Recorded metrics

Every live trial report records:

- Forge commit
- Fixture and task version
- Provider and exact model ID
- Thinking-mode setting
- Terminal run status and exit code
- Grader result
- Duration
- Model steps and tool calls by tool name
- Input, output, reasoning, and cached-token usage when returned by the provider
- Number of failed verification attempts
- Denied actions and reached limits

Cost may be derived in a report only when the pricing snapshot and retrieval
date are recorded. Forge must not bake changing provider prices into runtime
logic.

## Mandatory v0.1 release gates

- [x] All unit, integration, policy, and deterministic recovery tests pass.
- [x] The canonical fixture passes all public and hidden grader checks.
- [x] At least three fresh live canonical trials are recorded.
- [x] At least two of the three canonical live trials pass end to end.
- [x] At least two additional fixture tasks are measured and reported, even if
  their pass rate is lower.
- [x] Every reported run has a parseable trace consistent with tool and command
  results.
- [x] A completed interactive session survives process restart and can be
  continued by ID and through `--last` without restoring old approvals.
- [x] No trace, terminal output, fixture diff, or report contains the configured
  API key.
- [x] Outside-workspace file attempts and unapproved process commands are denied.
- [x] The interactive CLI passes deterministic tests for multi-line input,
  slash-command completion, workspace-file mentions, and exact diff review.
- [x] README setup, demo, results, limitations, and license match the tagged
  release.

Release reports must include failures. A low score is an engineering result to
improve, not a reason to remove unsuccessful trials.

## Explicit non-goals

The v0.1 evidence does not claim:

- General coding-task competence
- Protection equivalent to an operating-system sandbox
- Safe execution of arbitrary shell syntax
- File access outside the selected workspace
- Multiple providers, multiple agents, plugins, RAG, or persistent memory
- Deterministic behavior from a live model
