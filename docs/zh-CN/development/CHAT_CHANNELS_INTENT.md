# 聊天渠道接入 Intent

[English](../../development/CHAT_CHANNELS_INTENT.md) · [规格](CHAT_CHANNELS_SPEC.md) · [路线图](ROADMAP.md)

> 文档角色：current-development。0.4.0 已实现 Telegram 实验性功能。
> 维护者选择直接发布 0.4.0 CLI；下方原定预发布顺序被此决定取代。
> C10 完整真实验收仍未完成，不宣称全部验收门槛通过。

## 问题与预期结果

Forge 用户离开终端或桌面工作台后，仍需要委派和监督仓库任务。聊天入口应让已授权的
所有者在手机上提交任务、查看简短进度、批准具体操作、取消任务并接收结果。
任务仍在运行 Forge 的机器和绑定工作区中执行；接入聊天软件不会把本地仓库迁到云端。

首个完整流程是：在本地配置一个 Telegram bot，绑定一个工作区和一个所有者，在私聊中
发送编码任务、处理审批、收到结果，并在网关重启后继续对话。主机睡眠或离线时无法执行
任务，配置引导和状态展示必须说明这一点。

## 产品决策

- 将聊天渠道作为 Forge 的新增入口，复用 application/runtime。
- 首版限定 Telegram 私聊文本、一个 bot、一个所有者、一个工作区和一个活动任务；
  渠道边界应支持未来的平台扩展。
- 通过显式启动的前台 gateway 运行，独立于 Electron；后台服务安装和 Desktop 设置后续再做。
- 首版采用 Telegram long polling，无需公网入站地址；主机需要能访问 Telegram 和模型服务。
- 身份授权、任务归属和工作区绑定由宿主控制，不交给模型决定。
- 保留现有工具策略。远程接入不能隐式批准工具、启用插件、扩大文件访问或修改模型凭据。
- 消息以可读为目标：确认接收、报告重要阶段、返回简短结果，不持续转发原始 trace。

## 首版范围与非目标

| 首版包含 | 后续再做 |
| --- | --- |
| 显式所有者白名单、本地工作区绑定 | 公开 bot、群聊、团队权限、多用户 |
| 文本任务、持久化对话、状态、取消 | 语音、图片、任意文件上传、完整产物浏览器 |
| 单次有效且会过期的审批按钮 | 宽泛或永久远程授权 |
| 持久化消息接收、有限重试、中断状态报告 | 自动重放中断的工具执行 |
| 内部渠道契约、用于一致性测试的第二个假适配器 | 更多生产平台、第三方渠道市场 |
| 使用已配置模型适配器的 Forge 原生引擎 | 单独设计和验证后的远程 Codex 引擎支持 |
| CLI 网关生命周期和诊断 | Desktop 网关界面、跨渠道接续、定时任务 |

未来接入一个平台，应主要增加传输、身份接入、格式转换和能力适配，不重复实现任务执行
与权限策略。接入第二个真实平台后再评估抽象，暂不稳定公开插件 API。
消息适配器与 agent 工具插件是不同的扩展点。

## 用户体验与信任边界

只有身份验证和持久化成功后才能确认任务已接收。回复包含任务 ID 与绑定的工作区别名。
忙碌时明确回复 busy，不静默替换正在执行的任务。审批展示具体动作和范围；拒绝、超时或
审批状态丢失都不代表允许。模型运行或等待审批时，所有者仍可查询状态。

消息和选定结果会经过聊天平台，配置引导必须说明这一传输边界。默认回复不包含凭据、
隐藏推理或原始 trace。项目文件、工具输出、转发文本和仓库指令仍是不可信上下文，
不能授予发送者身份或审批权限。

## 成功标准与验收

完成状态以 spec 的验收矩阵为准，尤其包括：

1. 所有者能在真实私聊完成任务，验证持久化、审批与取消。
2. 白名单外账号不能触发模型或工具、查看状态、批准任务。
3. 重复消息和重启不会自动再次执行同一个已接收任务。
4. 中断任务明确显示 interrupted，已完成的对话历史可继续使用。
5. 现有 CLI/Desktop 行为和发布合同通过回归验证。
6. 第二个假适配器通过共享生命周期测试，core 中不出现 Telegram 类型。

离线测试、真实 Telegram/模型验收、npm 发布与 Desktop 发布分别记录，明确平台和
provider 的验证范围。

## 交付与版本意图

计划作为 0.4.0 功能版本交付，先提供如 0.4.0-beta.1 的预发布。
本次文档落地不修改包版本。发布准备时同步版本、CLI 打包资源、指南与发布说明，
内部实现包保持 private。Desktop 实际集成功能后可通过独立渠道发布，详见 spec。
